A Django-style web framework for Rust

Rangoli gives you what Django gives you: models, migrations, an admin, auth, forms, templates, a JSON API, background tasks and WebSockets. It adds what Django can't: queries the compiler checks, migrations that don't conflict across branches, async all the way down, safe defaults, and one fast binary to deploy. cargo add rangoli.

Get startedSource on GitHubSee the benchmarks

49 seconds, no sound: define models, run the commands, then the public pages, the admin, the JSON API and the task list of the example blog. Recorded from the real app.

Why it exists

Rust used to be hard to adopt because engineers who knew it were hard to find. Picking up a language is much faster now; what teams lack is a framework as complete as Django. Rangoli is that framework, with Django's shape and Rust's cost profile.

Async from the ground up
No sync views to convert, no ASGI migration, no sync_to_async tax. WebSockets are a handler.
Light
One binary. Admin, templates, real-time and each database driver are features you can leave out.
Never the reason you're down
Fuzzed on every push on three databases; outages give fast 503s and recover on their own.
Cheaper to run
On the same 4 cores: 5.3× Django's throughput on a database page, in 62 MB instead of 317 MB.

Get started

Add the crate

[dependencies]
rangoli = "0.2"
tokio = { version = "1", features = ["full"] }
serde = { version = "1", features = ["derive"] }

Describe your data

use rangoli::prelude::*;

#[derive(Model, Clone, Debug)]
#[model(table = "blog_post", display = "title")]
pub struct Post {
    pub id: Option<i64>,
    #[field(max_length = 200)]
    pub title: String,
    pub published: bool,
    #[field(auto_now_add)]
    pub created_at: DateTime,
}

#[tokio::main]
async fn main() -> rangoli::Result<()> {
    App::new()
        .admin::<Post>()
        .api::<Post>(Api::new().read(Access::Public))
        .run()
        .await
}

Run it

cargo run -- makemigrations
cargo run -- migrate
cargo run -- createsuperuser admin
RANGOLI_DEBUG=1 cargo run

Open http://127.0.0.1:8000/admin/ for the admin, /api/blog_post/ for the API and /api/schema.json for its OpenAPI document. Postgres or MySQL: set RANGOLI_DATABASE_URL.

What you get

Typed ORM
Post::objects().filter(Post::TITLE.contains("rust")): a misspelled field doesn't compile. Transactions, many-to-many, in_bulk and prefetch.
Migrations
Generated from your models, applied as a set so branches don't conflict. Postgres, MySQL and SQLite.
The admin
Django's admin, page for page: filters, search, actions, history, delete protection, password change.
JSON API
List, detail, create, update and delete with validation, pagination and filters, plus an OpenAPI schema.
Background tasks
Queued in your database, run by a worker in the same binary, with retries.
Pages and forms
Templates with Django 6.0 style partials, static files, and ModelForm returning typed models.

Measured against Django 6.1.2

The same blog (authors, posts, tags) written for each, loaded with identical data: 1,000 posts, 722 published, 2,000 tag links, on SQLite. Run on a 4-core Linux GitHub Actions runner, 64 concurrent connections for 15s after a warm-up, measured with oha; Django runs 4 gunicorn workers, django-bolt 4 processes, DEBUG off. Linux matters for django-bolt: on macOS its processes can't share the port's load. Shared runners are noisy, so compare frameworks within this run rather than across runs.

The first run went the other way. Rangoli was slower than Django on three of the four pages, and got slower as concurrency rose. Profiling showed every SQLite connection in the process waiting on SQLite's global mutexes for memory statistics and its shared page cache. Django never hits them, because each gunicorn worker is a separate process.

Rangoli now turns memory statistics off at runtime, and SQLite apps build SQLite without the shared page cache (.cargo/config.toml). The homepage went from 249 to 3,985 req/s. With Postgres or MySQL, neither applies.

Findings

Each finding runs the same code or command in both and shows the actual output, captured by bench/experiments.py.

A typo in a query

Both projects run a query on a field spelled titel instead of title.

Django 6.1.2

manage.py check reports System check identified no issues (0 silenced)., so the code ships. It fails when the line runs:
django.core.exceptions.FieldError: Cannot resolve keyword 'titel' into field. Choices are: author, author_id, body, created_at, id, published, rating, tags, title, updated_at

Rangoli

The program does not compile, so it never ships:
error[E0599]: no associated item named `TITEL` found for struct `Post` in the current scope
  --> src/main.rs:13:42
   |
 5 | pub struct Post {
   | --------------- associated item `TITEL` not found for this struct
...
13 |     let n = Post::objects().filter(Post::TITEL.eq("Hello")).count().await?;
   |                                          ^^^^^ associated item not found in `Post`

Every field lookup in Rangoli is a typed constant, so misspelled fields, comparing a text column with a number, and columns from another model are caught before deploy.

Two branches each add a migration

Two feature branches each add a column to a different table; both are merged and migrate runs.

Django 6.1.2

Exit code 1:
CommandError: Conflicting migrations detected; multiple leaf nodes in the migration graph: (0002_author_bio, 0002_tag_color in blog).
To fix them run 'python manage.py makemigrations --merge'

Rangoli

Exit code 0, both applied:
Applied 20261007120000_add_blog_author_bio
Applied 20261007120500_add_blog_tag_color
When two branches really do collide (both add the same column), Rangoli refuses and names both files:
Error: migration error: `20261007121000_add_blog_author_bio`: column `blog_author.bio` already exists (last changed by `20261007120000_add_blog_author_bio`; branches probably diverged)

Rangoli records the set of applied migrations instead of a chain, so unrelated work never needs a merge migration, while real conflicts are still caught.

N+1 queries

Both load the latest 50 published posts with each post's author and tags.

Django 6.1.2

Written the obvious way (post.author.name in a loop): 101 queries. With select_related and prefetch_related: 2 queries. Nothing warns you about the first version.

Rangoli

4 queries, measured with count_queries. A foreign key is an id, so there is no lazy post.author to call in a loop; related rows are fetched explicitly with in_bulk and prefetch.

Rangoli can't fall into the 101-query trap by accident, but tuned Django is better here: it joins authors in, and Rangoli has no join (select_related) yet. That is on the roadmap.

A new project's defaults

What django-admin startproject generates in Django 6.1.2, compared with Rangoli's defaults.

Django 6.1.2

DEBUG = True; a SECRET_KEY written into settings.py (yes); Content Security Policy middleware enabled: no (Django 6.0 added it as opt-in).

Rangoli

Debug is off unless RANGOLI_DEBUG=1; there is no secret key at all (sessions are random keys in the database and CSRF protection needs no token); a strict CSP is sent on every response.

Production-safe settings shouldn't be something you have to remember to change.

Guessing the admin password

Eight wrong passwords for admin, then the right one.

Django 6.1.2

Status codes: 200, 200, 200, 200, 200, 200, 200, 200. The correct password then logs in: guessing is unlimited without an extra package.

Rangoli

Status codes: 401, 401, 401, 401, 401, 401, 401, 401. The correct password then is refused: after five failures the username is locked for 15 minutes.

Cross-site login POSTs are rejected by both (Rangoli 403, Django 403). Rangoli's lockout is per process today; across several servers it needs a shared store.

Background tasks

Can the framework run a task in the background, out of the box?

Django 6.1.2

Django 6.x ships a tasks interface; its default backend is {'default': {'BACKEND': 'django.tasks.backends.immediate.ImmediateBackend'}}, which runs tasks immediately in the request. Worker commands in manage.py: none. Production use still means Celery plus Redis or RabbitMQ.

Rangoli

Tasks are queued in your database and run in the same binary: in-process by runserver, or by cargo run -- worker. Retries with backoff, caught panics, and recovery from crashed workers are built in.

One binary and your database instead of three moving parts.

What you deploy

The example blog app and everything it needs to run.

Django 6.1.2

42.8 MB of Python packages (5 of them) plus a Python runtime and gunicorn; 158 lines of app code across models, admin, views, URLs and settings.

Rangoli

One 13.0 MB binary with the admin's templates, CSS and JavaScript compiled in, plus your own templates; 87 lines of app code.

Both counts skip blank lines and comments.

Switching Django to an async server

The same Django app and views, served by gunicorn (WSGI) and by gunicorn with uvicorn workers (ASGI), on the Linux run.

Django 6.1.2

Under ASGI every sync view goes through sync_to_async. /hello: 4,555 → 793 req/s (83% slower). /posts.json: 973 → 447. Homepage: 227 → 135.

Rangoli

There is no sync mode to convert from: every handler, query and middleware is async, so WebSockets and long-lived connections need no change of server.

Moving an existing Django codebase to an async server makes it slower until every view is rewritten as async. That is the cost teams pay to add WebSockets to a sync Django app.

django-bolt

django-bolt puts a Rust (Actix) HTTP server in front of Django; handlers and the ORM stay in Python. It ran its async handler (the faster of its two modes) with as many processes as Django had workers.

django-bolt

/hello: 30,789 req/s, 6.8× plain Django. /posts.json: 878 req/s (plain Django: 973). Memory: 331 MB at rest, 7,844 MB after the load; in a local run one worker grew from about 40 MB to over 3 GB.

Rangoli

/hello: 69,071 req/s. /posts.json: 5,153 req/s. Memory after the same load: 62 MB.

django-bolt makes Django's HTTP layer fast; once a request reaches Python and the ORM it runs at Django's speed. The memory growth is what we measured, reproducible with bench/run.py; we have not looked for its cause.

Hostile input

SQL fragments, NUL bytes, 10,000-character values, impossible dates, numbers too big for any column and random JSON, thrown at every admin page and form, the JSON API and the login, on SQLite, Postgres and MySQL.

What the fuzzer caught

On Postgres, a NUL byte in a search term or a field was a 500: Postgres can't store NUL, while SQLite and MySQL accept it. Fixed: searches drop NUL; forms and the API refuse it with Django's own message, Null characters are not allowed.

Now

Zero server errors in 3,000 rounds (about 20,000 requests) on every push, on all three databases. A bug planted on purpose was caught within seconds.

Django has had this class of bug too; it is why its ProhibitNullCharactersValidator exists. A fuzzer that runs on every database finds the next one before users do.

The database goes away

Postgres is frozen (docker pause) and then restarted under a running app, in CI on every push.

Rangoli

Requests that need the database answer 503 with Retry-After within the database timeout instead of hanging; pages that don't need it keep working; when Postgres is back, so is the app, without a restart. A panicking handler costs one 500, and a stuck request is cut off after 30 seconds.

The framework is never the reason the backend goes down.

WebSockets

A chat room where every message reaches everyone in it.

Django 6.1.2

Channels, a Redis channel layer and an ASGI server (daphne or uvicorn): three more moving parts, plus the async-server slowdown above for the existing views.

Rangoli

One handler: realtime::serve(ws, &headers, "chat:lobby", |text| async move { Some(text) }), publish() from any view or task, and the same groups as Server-Sent Events. Cross-site handshakes are refused by default.

Real-time features don't require re-platforming the app.

Only what you use

An API-only service on Postgres.

Django 6.1.2

pip install django brings the whole framework: admin, templates, forms, sessions, i18n, whether the service uses them or not.

Rangoli

default-features = false, features = ["postgres"]: a 7.1 MB binary from 196 crates, against 13.1 MB and 249 crates with everything on.

Small services stay small, and switching a feature off never changes the database schema.

Where Django is still ahead

  • Twenty years of ecosystem. Thousands of packages, books, hosting guides and people who know it. Rangoli is brand new.
  • Joins. No select_related yet, so the example homepage takes 4 queries where tuned Django takes 2.
  • Admin depth. No inlines, custom actions, fieldsets, per-model permissions or groups.
  • The rest of the batteries. Internationalization, email, caching, password reset, savepoints in nested transactions, API tokens, and real-time groups across several servers are on the roadmap.
  • SQLite tuning. Getting full SQLite throughput needs one config file in your project. Postgres and MySQL need nothing.

The full list is in the README.

git clone https://github.com/Harshil-Jani/rangoli-rs && cd rangoli-rs
cargo build --release -p blog
cd bench && uv venv .venv && uv pip install --python .venv/bin/python "django==6.1.2" djangorestframework gunicorn "django-bolt==0.11.1" uvicorn uvicorn-worker
./setup.sh             # both databases, identical data
python run.py          # throughput, latency, memory, startup -> results/bench.json
python experiments.py  # the findings above -> results/experiments.json
